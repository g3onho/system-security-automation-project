## 1. 프로젝트 개요

KISA 「주요정보통신기반시설 기술적 취약점 분석·평가 가이드」 기준 점검은 보통 서버마다 사람이 직접 합니다.
서버가 늘수록 반복 작업이 많아지고, 점검자마다 판단이 달라지며, 무엇을 언제 고쳤는지 남지 않습니다.
게다가 취약점을 "고치는" 작업은 잘못하면 서비스 장애로 이어집니다.

| AS-IS (수동 점검) | TO-BE (SSAP) |
|---|---|
| 서버마다 직접 접속해 반복 점검 | 서버를 등록하면 Ansible이 여러 서버를 병렬 점검 |
| 점검자마다 판단 기준이 다름 | KISA 기준을 스크립트로 구현해 같은 기준으로 판정 |
| 조치가 장애로 이어질 위험 | 위험도로 자동조치 / 승인조치를 나누고, 조치 후 재점검 |
| 결과를 엑셀에 수작업으로 수집 | 모든 영역이 표준 JSON을 내고 DB에 자동 적재 |
| 조치 이력이 남지 않음 | 조치 전 백업, 작업마다 SHA-256 증적 |
| 보고서를 직접 작성 | 버튼 한 번으로 Excel·PDF 보고서 생성 |

**점검 범위**

| 영역 | 항목 | 자동조치 / 승인요청 | 대상 |
|---|---|---|---|
| UNIX | U-01 ~ U-67 (67개) | 22 / 45 | Rocky Linux 9·10, Ubuntu 24·26 |
| WEB | WEB-01 ~ WEB-26 (26개) | 11 / 15 | Apache(httpd), Nginx, Tomcat |
| DBMS | D-항목 10개 | 6 / 4 | MySQL 8.x |
| **합계** | **103개** | **39 / 64** | |

## 2. 전체 아키텍처

시스템은 **세 영역**으로 나뉩니다. 01 대시보드와 02 점검·조치 엔진은 컨트롤 노드에서, 03은 점검 대상 서버에서 동작합니다. 제가 맡은 SSH Host CA와 대시보드 개발은 6장에서 자세히 다룹니다.

![SSAP 전체 아키텍처](https://raw.githubusercontent.com/g3onho/system-security-automation-project/main/docs/images/architecture.png)

**읽는 법** — 01 대시보드와 02 점검·조치 엔진은 같은 컨트롤 노드에 있습니다. 관리자가 화면에서 대상과 영역을 골라 작업을 요청·승인하면, FastAPI와 작업 러너가 접속 대상의 신원(SSH Host CA)과 실행 조건(사전점검)을 확인한 뒤 02의 Ansible을 실행합니다. 03의 각 서버는 CA 호스트 인증서로 신원이 검증되고, 배포된 점검 릴리스로 점검·조치를 수행합니다. 서버의 결과는 02의 결과 JSON(`reports/`)으로 모이고, 01의 백엔드가 이를 MySQL에 적재해 화면과 보고서(Excel·PDF)의 근거로 씁니다. 실행 기록은 백엔드가 작업마다 SHA-256 증적으로 남깁니다.

| 영역 | 책임 | 주요 구성 | 자세한 설계 |
|---|---|---|---|
| 01 대시보드 | 대상 등록, 작업 요청·승인, 사전점검, 작업 실행·잠금, 결과 저장·조회, 증적 보존, 보고서 출력 | 화면, FastAPI, 작업 러너, 사전점검 게이트, SSH Host CA, MySQL·SQLite, 작업 증적 | [4](#4-실행-제어--신뢰-설계), [6](#6-나의-역할) |
| 02 점검 · 조치 엔진 | 점검 릴리스 배포, 점검·조치 플레이북 실행, 결과 수집 | Ansible (unix · web · dbms), 결과 JSON | [3](#3-핵심-설계--점검조치-엔진) |
| 03 점검 대상 | 점검·조치 스크립트 실행, 결과 생성 | webs, instructor_db, lecturedb (Tailscale) | [3](#3-핵심-설계--점검조치-엔진) |

**실행 흐름** (그림의 ①~⑧)

| 단계 | 실행 | 하는 일 |
|---|---|---|
| ① 요청 | 대시보드 | 대상 등록(인벤토리 자동 동기화), 진단 영역 선택, 작업 요청·승인 |
| ② 사전점검 | 백엔드 | SSH 신원 · 인증 · OS · sudo · 작업 충돌 확인, 실패 시 중단 |
| ③ 배포 | `deploy.yml` | 스크립트를 SHA-256 manifest 릴리스로 배포, 같은 릴리스면 생략 |
| ④ 점검 | `check.yml` | 읽기 전용 실행, 항목 수·중복·누락 검증 후 결과 JSON 수집 |
| ⑤ 자동조치 | `audit.yml` | `자동조치` 항목만 백업 후 수정하고 재판정 |
| ⑥ 승인조치 | `remediate_approved.yml` | 관리자가 고른 코드 + 확인 플래그가 있을 때만 조치, 이후 재점검 |
| ⑦ 적재 | 백엔드 | 결과 JSON을 MySQL에 저장, 작업마다 SHA-256 증적 생성 |
| ⑧ 표시·보고 | 대시보드 | 화면 3페이지(IP 등록 · 점검·조치 · 상세 분석)에 표시, Excel·PDF 보고서 생성 |

## 3. 핵심 설계 — 점검·조치 엔진

> KISA 기준을 코드로: 103개 항목을 같은 규칙으로 점검하고, 위험도에 따라 다르게 조치한다.

이 프로젝트의 중심은 KISA 기준을 실행 가능한 코드로 옮긴 **점검·조치 엔진**입니다. 세 영역이 같은 구조, 같은 판정 규약, 같은 결과 형식을 공유하도록 설계했습니다.

### 3-1. 영역별 독립 Ansible 프로젝트

```text
ansible/
├── unix/   U-01 ~ U-67
├── web/    WEB-01 ~ WEB-26
└── dbms/   D-항목 10개
    ├── check/       항목별 점검 스크립트 (읽기 전용)
    ├── fix/         항목별 조치 스크립트
    ├── lib/         공통 함수, 일괄 실행기
    ├── playbooks/   deploy · check · audit · remediate_approved
    ├── inventory/   대상 호스트 (대시보드가 자동 생성)
    ├── reports/     결과 JSON (실행 시 생성)
    └── tools/       릴리스 빌드
```

- 세 영역이 **같은 폴더 규칙과 같은 플레이북 이름**을 쓰기 때문에, 백엔드는 `runtime.py` 한 곳에서 영역별 경로만 바꿔 같은 방식으로 실행합니다. 결과의 코드 접두사로 영역을 판별합니다.
- 영역마다 따로 배포·검증할 수 있고, 새 영역도 같은 구조로 추가할 수 있습니다. 영역마다 다른 부분은 각 영역 `lib/` 안의 고유 모듈로만 둡니다.
  - UNIX는 `os_lib.sh`로 Rocky·Ubuntu를 식별해 배포판 차이를 처리합니다.
  - WEB은 `web_detect.sh`로 Apache·Nginx·Tomcat 중 설치된 웹 서버를 찾아 해당 설정을 점검합니다.
  - DBMS는 `mysql_lib.sh`와 접속 정보 템플릿(`templates/`)을 쓰고, 관리자 비밀번호는 **Ansible Vault**로 암호화했습니다.
- 세 영역 모두 같은 릴리스 방식(3-6)으로 배포되고, 대상 서버에서는 `current` 릴리스의 실행기가 점검 스크립트를 돌려 결과를 JSON Lines로 돌려줍니다.

### 3-2. 점검 스크립트 판정 규약

![점검·조치 엔진 — 점검 스크립트 · 조치 스크립트 · 공통 함수](https://raw.githubusercontent.com/g3onho/system-security-automation-project/main/docs/images/shell-scripts.png)

그림의 01은 릴리스 배포와 점검 경로(배치 실행기 → 항목 스크립트 → 판정 → 이중 판정 → 결과 JSON), 02는 위험도별로 나뉜 조치 경로(자동조치 · 승인조치)와 조치 스크립트의 내부 순서(승인 게이트 → 권한 확인 → 백업 → 변경 → 재판정), 맨 아래는 영역마다 같은 이름으로 제공되는 공통 함수입니다. 카드 오른쪽 위 꼬리표는 그 단계가 실행되는 곳(컨트롤 노드 · 대상 서버)입니다.

모든 점검 스크립트는 같은 형태입니다. 항목 메타데이터를 선언하고, `do_check` 함수가 **종료 코드로 판정**하며, 마지막에 공통 함수로 JSON을 출력합니다. 아래는 U-01 스크립트를 요약한 것입니다.

```bash
readonly ITEM_CODE="U-01"
readonly ITEM_TITLE="root 계정 원격 접속 제한"
readonly ACTION_TAG="승인요청"          # 자동조치 | 승인요청
readonly IMPACT="sshd 설정 적용을 위해 reload가 필요하며 관리자 재접속 경로에 영향"
readonly SEVERITY="상"                  # 상 | 중 | 하

do_check() {
    val="$(sshd -T | awk '/^permitrootlogin /{print $2}')"   # 실제 적용값 우선
    case "$val" in
        no|prohibit-password|without-password) return "$KISA_EXIT_GOOD" ;;  # 0 = 양호
        yes|"")                                 return "$KISA_EXIT_VULN" ;;  # 1 = 취약
    esac
    # 설정을 읽을 수 없으면                       return "$KISA_EXIT_FAIL"     # 2 = 판정 불가
}

verify_and_get_status do_check          # 같은 판정을 두 번 실행해 비교
print_json_result "$ITEM_CODE" "$ITEM_TITLE" "$KISA_STATUS" "점검" "$CHECK_DETAIL" ...
```

| 규약 | 내용 |
|---|---|
| 종료 코드 | 양호 `0` · 취약 `1` · 판정 불가 `2`. 그 밖의 코드는 실행기가 `fail`로 처리 |
| 이중 판정 | `verify_and_get_status`가 판정 함수를 두 번 실행하고, 결과가 다르면 점검 중 설정이 바뀐 것으로 보고 `fail` |
| 판정 근거 | `CHECK_DETAIL`에 "무엇을 봤고 왜 그렇게 판정했는지"를 문장으로 남김 (보고서의 진단 근거) |
| 보수적 판정 | 설정이 없거나 해석할 수 없으면 양호로 넘기지 않고 취약 또는 `fail` |
| OS 식별 | `/etc/os-release`로 Rocky·Ubuntu 등을 식별해 같은 스크립트가 배포판 차이를 처리 |

### 3-3. 배치 실행기 `run_checks.sh`

항목마다 원격 접속하면 67번 SSH 왕복이 생깁니다. 그래서 대상 서버에 실행기를 두고 **원격 호출 한 번으로 전 항목을 실행**합니다.

- 항목마다 제한 시간(기본 120초)을 걸고, 시간 초과·스크립트 누락·규약 밖 종료 코드·잘못된 JSON은 모두 **`fail` 결과 JSON으로 바꿔** 결과 개수가 줄지 않게 합니다.
- 각 결과에 `release_hash`(어떤 릴리스로 점검했는지)와 `duration_seconds`를 붙여 JSON Lines로 출력합니다.
- `check.yml`은 결과를 파싱한 뒤 **개수(67개)·중복·누락을 검증**하고, 하나라도 맞지 않으면 실패로 처리합니다.

### 3-4. 공통 결과 스키마

세 영역 모두 같은 형식의 JSON을 냅니다. 코드 접두사(`U-` / `WEB-` / `D-`)만으로 영역을 분류하므로, **하나의 DB·채점 로직·화면으로 세 영역을 관리**합니다.

```json
{
  "code": "U-02", "title": "비밀번호 관리정책 설정",
  "status": "취약", "action": "점검", "severity": "상", "action_tag": "자동조치",
  "detail": "비밀번호 관리정책 미흡: 최근 비밀번호 기억=미적용(4회 이상 및 PAM 연동 필요)",
  "impact": "설정 파일 값만 변경되며 서비스 재시작이 불필요함",
  "os_type": "rocky 9.8", "timestamp": "2026-08-30T18:12:31+09:00",
  "release_hash": "0159deaf…", "duration_seconds": 0
}
```

| 필드 | 의미 | 만드는 곳 |
|---|---|---|
| `code`, `title` | 항목 코드·이름 (접두사 = 영역) | 점검 스크립트 |
| `status` | 양호 · 취약 · fail | 점검 스크립트 |
| `action` | 점검 · 조치 (어느 단계의 결과인지) | 점검·조치 스크립트 |
| `severity` | 상 · 중 · 하 (채점 가중치) | 점검 스크립트 |
| `action_tag` | 자동조치 · 승인요청 (조치 권한 게이트) | 점검 스크립트 |
| `detail`, `impact` | 판정 근거, 조치 시 예상 영향 | 점검 스크립트 |
| `os_type`, `timestamp` | OS·서비스 버전, 실행 시각 | 공통 라이브러리 |
| `release_hash`, `duration_seconds` | 점검에 쓴 릴리스, 소요 시간 | 배치 실행기 |

### 3-5. 점검 → 자동조치 → 승인조치 → 재점검

조치가 서비스에 주는 영향으로 두 가지로 나눴습니다.

| 기준 | 자동조치 (39개) | 승인요청 (64개) |
|---|---|---|
| 서비스 영향 | 설정 값만 변경, 재시작 불필요 | 접속·세션에 영향 가능 |
| 되돌리기 | 백업으로 즉시 복구 | 잘못되면 관리자도 접속 불가 |
| 예시 | U-02 비밀번호 정책 값 | U-01 root 원격 접속 차단, U-03 PAM 계정 잠금 |
| 실행 | `audit.yml`이 점검 직후 실행 | `remediate_approved.yml`이 승인된 코드만 실행 |

| 플레이북 | 하는 일 | 안전장치 |
|---|---|---|
| `check.yml` | 읽기 전용 점검, 결과 JSON 저장 | 배포 여부 확인, 결과 완전성 검증 |
| `audit.yml` | 점검 결과에서 **취약 + 자동조치** 항목만 골라 조치 | 점검 리포트가 없으면 중단 |
| `remediate_approved.yml` | 관리자가 고른 코드만 조치 후 재점검 | **선택 코드 + `kisa_confirm=true`** 둘 다 있어야 실행, 코드 형식·범위 검증 |

조치 스크립트의 공통 규칙은 다음과 같습니다.

1. 승인요청 항목은 `KISA_APPROVAL=true` 환경변수가 없으면 스스로 조치를 보류합니다.
2. 바꾸기 전에 원본을 타임스탬프로 백업합니다.
3. 조치 후 **같은 판정 함수를 두 번 실행**해 최종 상태를 정하고, 두 결과가 다르면 `fail`로 처리합니다.
4. 허용 IP처럼 관리자만 알 수 있는 값이 필요한 항목(TCP Wrappers, NFS, SNMP 등)은 값이 주어지지 않으면 조치를 보류합니다. 관리자 자신의 접속이 끊기는 것을 막기 위해서입니다.
5. DBMS 승인조치는 이미 실행한 자동조치 항목을 다시 실행하지 않습니다.

### 3-6. 무결성 있는 배포

점검 스크립트 자체가 바뀌면 결과를 믿을 수 없습니다. 그래서 스크립트는 **검증 가능한 릴리스**로만 배포합니다.

| 단계 | 내용 |
|---|---|
| 빌드 (컨트롤 노드) | `check/ fix/ lib/` 파일 전체의 SHA-256 manifest를 만들고, **manifest의 해시를 릴리스 ID**로 사용. 같은 내용이면 같은 ID |
| 전송 | 대상에 같은 릴리스가 이미 검증된 상태로 있으면 전송 생략 |
| 검증 (대상 서버) | manifest 해시 일치, 파일 개수 일치, 점검·조치 스크립트 개수(UNIX 67/67), 실행기 존재, 심볼릭 링크 없음 |
| 전환 | 검증을 통과한 릴리스만 `current` 심볼릭 링크를 **원자적으로 교체**. 손상된 기존 릴리스는 격리 |
| 동시성 | 배포는 배타 잠금, 점검 실행기는 공유 잠금(`flock`)을 잡아 배포 중 점검이 섞이지 않음 |

## 4. 실행 제어 · 신뢰 설계

> root 권한으로 설정을 바꾸는 도구이므로, 실행 전에 접속 대상과 실행 조건을 검증한다.

### 4-1. 사전점검 게이트

모든 작업은 원격 실행 전에 서버마다 다섯 가지를 확인합니다. 하나라도 실패하면 원격 작업을 시작하지 않고, 실패한 검사와 **직접 확인할 명령어**를 대시보드에 보여 줍니다.

| 순서 | 검사 | 통과 조건 | 실패 시 안내 |
|---|---|---|---|
| 1 | SSH 신원 | 승인된 호스트 키 또는 CA 인증서와 일치 | 서버 콘솔에서 지문 확인 명령어 |
| 2 | SSH 인증 | 공개키 인증 성공 | `ssh -vv` 진단 명령어 |
| 3 | 지원 OS | Rocky / RHEL / CentOS / AlmaLinux / Ubuntu / Debian | `/etc/os-release` 확인 |
| 4 | 비대화형 sudo | `sudo -n` 성공 | `sudo -l` 확인 |
| 5 | 작업 충돌 | 같은 서버에 실행 중인 작업 없음 | 대기 후 재실행 |

앞 단계가 실패하면 뒤 단계는 "건너뜀"으로 표시해, 원인을 한 곳으로 좁혀 줍니다.

### 4-2. SSH Host CA

CA가 호스트명·IP로 서명한 인증서(유효 52주)가 있는 서버에만 접속하고, 대시보드가 실행하는 모든 플레이북에 `StrictHostKeyChecking=yes`를 강제합니다. 신원 확인은 사전점검 1단계로 연결됩니다.
제가 설계·구현한 부분이라 [6-1](#6-1-ssh-host-ca-기반-접속-대상-검증--설계구현)에서 자세히 설명합니다.

### 4-3. 작업 러너와 서버 단위 잠금

| 항목 | 설계 |
|---|---|
| 작업 종류 | `check`(점검 + 자동조치), `check-only`(점검만), `remediate`(승인조치) |
| 실행 방식 | 요청을 받으면 작업 ID를 만들고 백그라운드 스레드에서 `사전점검 → 배포 → 점검 → 적재 → 자동조치 → 적재` 순서로 실행 |
| 서버 잠금 | 작업 시작 시 대상 서버 전체에 잠금을 걸고(SQLite 트랜잭션), 이미 잠긴 서버가 있으면 작업을 거부 |
| 장애 대비 | 플레이북 실행 제한 30분, 오래된 잠금(35분 이상 갱신 없음)은 자동 정리. 작업이 실패해도 증적 생성과 잠금 해제는 반드시 실행 |
| 상태 저장 | 작업·잠금·호스트 신원·감사 기록은 SQLite, 점검 결과는 MySQL로 분리 |

### 4-4. 인증 · 세션 · 인벤토리

- **로그인** : 비밀번호는 PBKDF2-SHA256 해시로만 저장합니다. 세션 토큰은 원문 대신 SHA-256 해시를 저장하고, 8시간 후 만료됩니다.
- **신원 변경 API 보호** : SSH 지문 승인 · CA 초기화 · 인증서 배포 API는 세션 토큰을 확인하고, 관리자 비밀번호를 한 번 더 받습니다.
- **인벤토리 동기화** : 대시보드에서 서버를 등록·삭제하면 영역별 인벤토리와 통합 인벤토리를 다시 생성합니다. 반쯤 쓰인 파일을 읽지 않도록 임시 파일에 쓴 뒤 원자적으로 교체합니다.

## 5. 결과 · 증적 · 보고 설계

> 모든 숫자는 DB의 결과에서, 모든 실행은 증적으로 다시 확인할 수 있게 한다.

### 5-1. 데이터 모델

| 저장소 | 테이블 | 내용 |
|---|---|---|
| MySQL | `check_results` | 서버 × 항목별 **최신 결과** (서버·코드 기준 upsert, 결과 JSON 원문 보존) |
| MySQL | `check_runs` | 점검·조치 1회마다의 **실행 이력** (영역, 실행 종류, 양호·취약·자동·승인 건수) |
| MySQL | `registered_hosts` | 등록 서버와 진단 영역 |
| MySQL | `report_logs` | 보고서 생성 조건·생성자·시각 |
| MySQL | `login_users` | 콘솔 사용자 (PBKDF2 해시) |
| SQLite | `jobs`, `locks`, `identities`, `host_certificates`, `identity_audit`, `api_sessions` | 작업 상태, 서버 잠금, SSH 신원·인증서, 신원 감사, 세션 |

결과 JSON을 컬럼으로 쪼개지 않고 원문으로 저장해, 점검 필드가 늘어나도 DB 스키마를 바꾸지 않도록 했습니다.

**두 저장소로 나눈 이유** — MySQL에는 화면과 보고서가 함께 읽는 결과 데이터(결과 · 이력 · 사용자)를, SQLite에는 컨트롤 노드 한 곳에서만 쓰는 실행 상태(작업 · 잠금 · 신원 · 세션)를 두었습니다. 결과 DB에 문제가 생겨도 잠금과 신원 확인 같은 안전장치는 따로 동작합니다.

## 6. 나의 역할

| 담당 | 한 일 |
|---|---|
| **SSH Host CA** (설계·구현) | 호스트 키 검증을 끈 자동화의 위험을 짚고, CA 서명 인증서 기반 검증으로 전환. 실패 시 원복되는 안전 배포 구현 |
| **대시보드 개발** (FastAPI 백엔드 · 웹 프론트엔드) | 작업 러너·서버 잠금·사전점검·증적을 맡는 FastAPI 백엔드와 IP 등록·점검·조치·상세 분석 화면 개발 |
| 점검 스크립트 검증 (팀 공동) | 대상 서버에서 점검·조치 스크립트를 실행해 결과 검증 |

### 6-1. SSH Host CA 기반 접속 대상 검증 — 설계·구현

**문제** — 초기 Ansible 설정은 빠른 실행을 위해 호스트 키 검증을 꺼 두었습니다(`host_key_checking = False`).
SSAP는 root 권한으로 설정을 바꾸기 때문에, IP가 바뀌었거나 다른 서버가 응답해도 그 서버를 그대로 "조치"하게 됩니다. 반대로 검증을 켜면 서버마다 호스트 키를 확인·등록해야 해서, 서버가 늘수록 SSH 연결 관리가 복잡해집니다.

**선택지 비교**

| 방식 | 장점 | 단점 |
|---|---|---|
| 호스트 키 검증 끄기 (기존) | 설정 불필요 | 접속 대상을 전혀 확인하지 않음 |
| 서버별 호스트 키 수동 등록 | 안전 | 서버 수만큼 키 관리, 재설치마다 재등록 |
| **SSH Host CA (선택)** | CA 공개키 한 줄로 전체 신뢰, 만료·폐기를 한곳에서 관리할 수 있는 구조 | 첫 신뢰를 맺는 절차가 필요 |

**왜 SSH Host CA인가 — 서버가 늘어나는 상황을 전제로** — 실습에서 다룬 서버는 3대뿐이지만, 이 프로젝트가 지향하는 것은 **여러 대의 서버를 한 번에 점검·조치하는 자동화**입니다. 그런데 모든 작업은 SSH로 접속해서 이뤄지고, 서버마다 호스트 키를 확인하고 등록하는 과정은 서버 수만큼 늘어납니다. 서버를 추가하거나 재설치할 때마다 키를 다시 맞춰야 해서, 대수가 많아질수록 SSH 연결을 관리하는 일 자체가 복잡해집니다.

SSH Host CA를 쓰면 컨트롤 노드는 **CA 공개키 한 줄만 신뢰**하면 되고, 서버는 CA가 서명한 인증서만 받으면 됩니다. 서버가 몇 대든 같은 신뢰 기준이 그대로 적용됩니다.

**완벽하지 않은 걸 알면서도 지금 넣은 이유** — 2주 실습에서 운영 수준의 CA(첫 신뢰 검증, CA 키 보호, 인증서 폐기·갱신)까지 만들 수 없다는 건 알았습니다. 그래도 서버가 3대일 때 이 구조가 실제로 동작하는지 먼저 확인해 두면, 서버가 늘어날 때 같은 방식으로 넓힐 수 있다고 판단했습니다. 대신 실습이라 생략한 부분은 숨기지 않았습니다.

첫 등록 서버는 **서버 콘솔에서 직접 확인한 호스트 키 지문(SHA256 해시)과 네트워크로 조회한 지문을 대조해 승인(trusted)한 뒤** 인증서를 배포합니다. 실습 편의를 위해 처음 본 키를 바로 신뢰하는 bootstrap 경로도 두었고, 이 경로는 감사 로그에 `auto_trusted_lab`으로 따로 남습니다.

![SSH Host CA 신뢰 수립과 검증 흐름](https://raw.githubusercontent.com/g3onho/system-security-automation-project/main/docs/images/ssh-ca-flow-mine.png)

서버 신원은 `등록 → pending → trusted → certified` 순서로 올라가고, 키가 바뀌면 `changed`가 되어 작업이 차단됩니다. 신원과 관련된 모든 동작(지문 승인, bootstrap, 인증서 배포, 재인증 실패 포함)은 감사 기록으로 남습니다.

**구현**

| 단계 | 내용 |
|---|---|
| CA 준비 | `ssh-keygen -t ed25519`로 Host CA 생성, 개인키 `0600`, 저장 위치(`runtime/`)는 Git 제외 |
| 첫 신뢰 | 콘솔에서 확인한 호스트 키 지문 = 네트워크 조회 지문일 때만 승인(관리자 재인증), 불일치·조회 중 키 변경은 거부 |
| 신원 서명 | 호스트명·IP를 principal로 넣은 호스트 인증서 발급, 유효기간 52주 |
| 안전 배포 | `sshd_config` 백업 → 인증서 설치 → `sshd -t` → reload, 실패하면 즉시 원복 |
| 재검증 | 배포 후 네트워크로 인증서를 다시 조회해 CA 서명 확인 |
| 검증 강제 | `known_hosts`에 `@cert-authority` 등록, 플레이북에 `StrictHostKeyChecking=yes`, 사전점검 1단계로 연결 |
| 감사 | 지문 승인·bootstrap·인증서 배포를 승인자·관측 지문·결과와 함께 기록 |

```bash
# 호스트 인증서 발급
ssh-keygen -s runtime/ssh_host_ca -h \
  -I "ssap:<hostname>:<ip>:<serial>" \
  -n "<hostname>,<ip>" \
  -V -5m:+52w \
  host_key.pub
```

```bash
# 대상 서버 배포 스크립트 (요약) — 실패하면 원래 설정으로 되돌린다
backup=/etc/ssh/sshd_config.ssap-backup-$(date +%Y%m%d%H%M%S)
sudo cp -a /etc/ssh/sshd_config "$backup"
# ... 인증서 설치, HostCertificate 설정 추가 ...
if ! sudo sshd -t; then                 # 문법 오류 → 원복
  sudo cp -a "$backup" /etc/ssh/sshd_config; exit 20
fi
if ! sudo systemctl reload sshd; then   # reload 실패 → 원복 후 재기동
  sudo cp -a "$backup" /etc/ssh/sshd_config; exit 21
fi
```

**결과 — 된 것, 부분적으로 된 것, 하지 못한 것**

*된 것*

- 등록 서버 3대에 인증서를 배포해 모두 certified(화면의 "CA 인증") 상태로 점검을 준비했습니다.
- 배포는 백업 → `sshd -t` → reload 순서로 하고, 실패하면 원복하는 경로까지 구현했습니다. 배포 후 다시 조회해 CA 서명을 확인한 서버만 certified가 됩니다.
- 대시보드가 실행하는 작업은 `StrictHostKeyChecking=yes`와 `@cert-authority` known_hosts로 접속하고, pending·changed 서버는 사전점검 1단계에서 차단됩니다.
- 첫 신뢰는 콘솔 지문 대조 승인으로 구현했습니다. 지문이 다르거나 조회 중 키가 바뀌면 거부합니다.
- 지문 승인·CA 초기화·인증서 배포는 관리자 비밀번호를 다시 확인하고, 성공·실패 모두 감사 기록에 남습니다.

*부분적으로 된 것*

- **첫 신뢰** — 처음 접속한 서버가 진짜인지 지문 대조로 확인하도록 만들었지만, 실습 편의를 위해 이 확인을 건너뛰고 처음 받은 키를 그대로 믿는 경로(bootstrap)도 남겨 두었습니다. 이 경로를 쓰면 기록에 `auto_trusted_lab`으로 표시되지만, 첫 접속 순간 가짜 서버가 응답하면 걸러내지 못합니다(TOFU의 한계).
- **검증 강제** — 대시보드 경로에만 적용됩니다. `ansible/unix`·`ansible/web`의 `ansible.cfg`는 `host_key_checking = False`라, 대시보드 없이 수동 실행하면 검증이 빠집니다.
- **CA 개인키 보호** — 권한 `0600`, Git 제외, 관리자 재확인까지만 했습니다. 키에 암호가 없고(`-N ""`) 대시보드와 같은 컨트롤 노드에 파일로 있습니다.

*하지 못한 것*

- 인증서 폐기 목록(KRL)과 만료 전 자동 갱신 — 키가 유출돼도 즉시 무효화하지 못합니다.
- CA 키를 HSM·Vault 같은 별도 서명 서비스로 분리하는 것, CA 교체(rotation).
- 서버가 많은 환경에서의 검증.

정리하면 **"자동화가 엉뚱한 서버에 접속해 조치하지 않게 막는 장치"는 동작하지만, CA 자체를 지키는 운영 수준의 장치는 없다**가 이 구현의 정확한 범위입니다.

**운영으로 옮긴다면 이 순서로** — ① 수동 실행용 `ansible.cfg`도 호스트 키 검증 켜기(설정 한 줄) → ② bootstrap 경로를 막고 지문 대조 승인만 허용 → ③ CA 개인키를 별도 서명 서비스로 분리 → ④ KRL과 자동 갱신 추가.

![CA 인증 상태](https://raw.githubusercontent.com/g3onho/system-security-automation-project/main/docs/images/ca-status.png)

![SSH Host CA 인증 상세 — 배포 검증 · 재검증 · 감사 이력](https://raw.githubusercontent.com/g3onho/system-security-automation-project/main/docs/images/ca-detail.png)

실제 대시보드의 CA 인증 상세 화면입니다. ① Host CA 준비 → ② 지문 승인 → ③ 인증서 발급·배포 → ④ sshd 반영 검증 → ⑤ 네트워크 재검증 순서가 그대로 보이고, 감사 이력에는 실습용 bootstrap(`auto_trusted_lab`)과 인증서 배포(`certificate_approved`)가 남아 있습니다.

## 7. 트러블슈팅

### ① 자동조치가 끝났는데 취약이 그대로였다 (U-02)

- **현상** — U-02(비밀번호 관리정책) 자동조치 후 재점검 결과가 여전히 취약. 조치 업데이트에 "미조치 2건"으로 표시.
- **원인** — 조치 스크립트는 `login.defs`, `pwquality.conf`와 `pwhistory.conf`의 `remember=4`까지 설정하지만, PAM 스택에 `pam_pwhistory`를 연결하지는 않습니다. 판정 기준이 "최근 비밀번호 4회 기억 + PAM 연동"이라 취약으로 남았습니다.
- **판단** — PAM 스택 수정은 잘못되면 모든 로그인 경로가 잠길 수 있어, U-03처럼 일부러 자동조치에서 뺀 영역입니다. 자동조치 범위를 넓히지 않고 남은 부분을 승인 경로로 넘겼습니다.
- **배운 점** — 조치 스크립트의 종료 코드만 믿었다면 "조치 완료"로 기록됐을 것입니다. 조치 후 재판정(3-5)과 조치 전후 비교 화면(6-2)이 거짓 성공을 막았습니다.

### ② 두 세대의 결과 스키마가 섞여 집계가 어긋났다

- **원인** — 초기 DBMS 결과는 `rule`, 영문 `status`(`PASS`) 등 필드 4개였고 조치 권한 필드가 없었습니다. 컨트롤 노드에 구버전·신버전 리포트가 함께 남아 있었습니다.
- **해결** — 모든 영역을 공통 스키마(3-4)로 통일하고 `action_tag`를 승인 게이트에 연결했습니다. 이후 코드 접두사만으로 영역을 분류하고 같은 채점 기준을 적용할 수 있게 됐습니다.

## 9. 회고

**배운 점**

- **자동화 도구도 공격 표면이다.** 실행 편의를 위해 끈 검증 하나가, root로 설정을 바꾸는 도구와 만나면 큰 위험이 됩니다.
- **바꾸는 작업은 되돌릴 수 있어야 한다.** 인증서 배포와 조치 스크립트 모두 백업 → 검사 → 적용 → 실패 시 원복 순서를 지켰습니다.
- **조치와 해결은 다르다.** 재점검으로 확인하기 전까지는 고쳐진 것이 아닙니다.
- **형식을 먼저 합의해야 한다.** 결과 스키마를 늦게 통일한 대가를 통합 테스트에서 치렀습니다.

**한계와 개선 방향**

- Windows 점검 미지원, DBMS는 MySQL 10개 항목.
- 서버 장애·네트워크 단절 같은 예외 처리 보완 필요.
- Host CA는 실습용 구성입니다. 실습용 bootstrap 경로(첫 키 자동 신뢰), 암호 없는 CA 개인키, 폐기·갱신 부재, 수동 실행 시 검증 누락을 [6-1](#6-1-ssh-host-ca-기반-접속-대상-검증--설계구현)의 표에 정리했습니다.
- 판정 불가(N/A) 항목을 지표마다 다르게 셌습니다(부록 A). 상태 정의를 통일해야 합니다.
- 세션 토큰 검사는 SSH 신원 · CA API에만 적용했습니다. 점검 실행 · 결과 조회 API까지 같은 인증을 거치도록 넓혀야 합니다.

## 부록 A. 보안 점수 산정 방식

같은 점검 결과를 목적에 따라 세 가지 지표로 봅니다.

| 지표 | 계산식 | 쓰는 곳 |
|---|---|---|
| 양호율 | 양호 ÷ 전체 항목 | 점검·조치 화면 |
| 보안 준수율 | 양호 ÷ (양호 + 취약) | Excel 보고서 (N/A 제외) |
| **보안 점수** | (배점 합 − 감점) ÷ 배점 합 × 100 | 상세 분석, 등급 산정 |

| 중요도 | 배점 | | 상태 | 감점 |
|---|---|---|---|---|
| 상 | 10 | | 양호 | 0% |
| 중 | 8 | | 일부조치 | 50% |
| 하 | 6 | | 취약 · 점검필요 | 100% |

| 등급 | 우수 | 양호 | 보통 | 미흡 | 취약 |
|---|---|---|---|---|---|
| 점수 | 91 이상 | 81 ~ 91 | 71 ~ 81 | 61 ~ 71 | 61 미만 |

**왜 가중치인가** — 양호율에서는 "root 원격 접속 허용(상)"과 "불필요한 그룹 존재(하)"가 똑같이 1건입니다. 가중 점수는 중요한 항목이 취약할수록 크게 깎여, 점수와 조치 우선순위가 같은 방향을 가리킵니다.

**계산 예시 (2026-08-30 운영 상태 점검)**

| 서버 | 항목 | 배점 합 | 감점 | 보안 점수 | 등급 |
|---|---|---|---|---|---|
| webs | 93 | 802 | 취약 상 6 · 중 1 · 하 1 → 74 | 90.8 | 양호 |
| instructor_db | 77 | 666 | 취약 상 3 · 중 1 · 하 1, 점검필요 중 1 → 52 | 92.2 | 우수 |

webs는 양호율(91.4%)로는 instructor_db와 비슷하지만, 상 등급 취약 6건 때문에 점수가 더 깎여 등급이 한 단계 낮습니다.

> PDF 보고서의 "승인조치 후 점수"는 남은 취약 항목을 **모두 조치에 성공했다고 가정한 예상치**라 성과에 쓰지 않았습니다.

**남은 과제** — 판정 불가 항목(D-06)을 보안 점수는 100% 감점, Excel 준수율은 분모에서 제외, PDF는 취약으로 표기했습니다. 그래서 같은 회차인데도 취약 건수가 화면마다 13건 / 14건으로 달랐습니다.
