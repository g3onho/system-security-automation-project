# KISA 기준 보안 점검 자동화 플랫폼 SSAP 회고 — 전체 설계부터 내가 맡은 SSH Host CA까지

2주 동안 4명이 함께 **KISA 가이드 기반 취약점 진단·조치 자동화 플랫폼(SSAP)** 을 만들었습니다.
서버를 등록하면 Ansible이 103개 항목을 점검하고, 취약한 항목을 자동으로 또는 관리자 승인을 받아 고친 뒤, 결과를 대시보드와 보고서로 보여 주는 시스템입니다.

이 글은 먼저 **프로젝트 전체 설계**를 자세히 정리하고, 그다음 제가 맡은 **SSH Host CA 기반 접속 대상 검증**과 **대시보드 개발**을 다룹니다.

> 코드: [github.com/g3onho/system-security-automation-project](https://github.com/g3onho/system-security-automation-project)

---

## 1. 왜 만들었나

KISA 「주요정보통신기반시설 기술적 취약점 분석·평가 가이드」는 서버·웹·DB 보안 설정을 항목별로 점검하는 기준입니다. 문제는 이 점검을 대부분 사람이 한다는 점입니다.

- 서버마다 접속해서 설정 파일을 열어 보고
- 결과를 엑셀에 옮겨 적고
- 같은 항목도 점검자마다 판단이 다르고
- 무엇을 언제 고쳤는지 기록이 남지 않습니다.

여기에 하나가 더 있습니다. 취약점을 **고치는** 작업은 잘못하면 서비스 장애로 이어집니다. root 원격 접속을 막다가 관리자 자신이 서버에 못 들어가게 되는 식입니다.

그래서 목표를 이렇게 잡았습니다. **기준은 스크립트로, 실행은 Ansible로, 판단과 기록은 대시보드로.** 그리고 조치는 위험도에 따라 사람이 끼어들 자리를 남겨 둔다.
점검 범위는 UNIX 67개(Rocky Linux·Ubuntu), WEB 26개(Apache·Nginx·Tomcat), DBMS 10개(MySQL), 모두 103개 항목입니다.

## 2. 전체 아키텍처

시스템은 세 영역으로 나뉩니다. 01 대시보드와 02 점검·조치 엔진은 컨트롤 노드에서, 03은 점검 대상 서버에서 동작합니다. 제가 맡은 SSH Host CA와 대시보드 개발은 6장에서 자세히 다룹니다.

![SSAP 전체 아키텍처](https://raw.githubusercontent.com/g3onho/system-security-automation-project/main/docs/images/architecture.png)

- **01 대시보드** : 관리자가 화면에서 대상을 등록하고 작업을 요청·승인합니다. FastAPI가 작업 러너에 넘기면, 러너는 서버 단위 잠금과 사전점검을 거친 뒤 Ansible을 실행하고 작업마다 SHA-256 증적을 남깁니다. 접속 대상의 신원은 SSH Host CA로 검증하고, 결과는 저장소(MySQL)에 적재해 화면과 Excel·PDF 보고서로 보여줍니다.
- **02 점검 · 조치 엔진** : 영역별 Ansible 프로젝트가 점검 릴리스를 배포하고 점검·조치 플레이북을 실행해, 서버의 결과를 JSON(`reports/`)으로 모읍니다.
- **03 점검 대상** : Tailscale 네트워크로 연결된 서버가 배포된 점검 릴리스로 점검·조치를 수행합니다.

작업 하나는 그림의 ①~⑧ 순서로 흘러갑니다. 위쪽 줄은 요청·실행(①~⑥)으로 오른쪽으로, 아래쪽 줄은 결과·보고(⑦~⑧)로 다시 화면으로 돌아옵니다.

```text
① 요청 → ② 사전점검 → ③ 배포 → ④ 점검 → ⑤ 자동조치 → ⑥ (관리자 승인) 승인조치 + 재점검 → ⑦ 적재 → ⑧ 화면 표시·보고서
```

## 3. 핵심 설계 — KISA 기준을 코드로 옮긴 점검·조치 엔진

이 프로젝트의 중심은 점검·조치 엔진입니다. 103개 항목을 세 영역에서 **같은 구조, 같은 판정 규약, 같은 결과 형식**으로 다루는 게 설계의 핵심이었습니다.

### 영역별 독립 Ansible 프로젝트

UNIX·WEB·DBMS는 각각 독립된 Ansible 프로젝트지만, 폴더 규칙은 똑같습니다.

```text
ansible/
├── unix/   U-01 ~ U-67
├── web/    WEB-01 ~ WEB-26
└── dbms/   D-항목 10개
    ├── check/       항목별 점검 스크립트 (읽기 전용)
    ├── fix/         항목별 조치 스크립트
    ├── lib/         공통 함수, 일괄 실행기
    ├── playbooks/   deploy · check · audit · remediate_approved
    ├── inventory/   대상 호스트 (대시보드가 자동 생성)
    ├── reports/     결과 JSON (실행 시 생성)
    └── tools/       릴리스 빌드
```

규칙이 같으니 백엔드는 `runtime.py` 한 곳에서 영역별 경로만 바꿔 같은 방식으로 실행할 수 있고, 영역마다 따로 배포·검증할 수도 있습니다. 영역마다 다른 부분은 각 영역 `lib/` 안의 고유 모듈(OS 식별, 웹 서버 탐지, MySQL 접속)로만 둡니다. DBMS는 MySQL 관리자 비밀번호를 Ansible Vault로 암호화했고, WEB은 설치된 웹 서버(Apache·Nginx·Tomcat)를 먼저 찾아 그에 맞는 설정을 봅니다.

### 판정 규약: 종료 코드로 말한다

점검 스크립트, 배치 실행기, 조치 스크립트, 공통 라이브러리가 어떻게 맞물리는지 먼저 그림으로 보면 이렇습니다. 위쪽은 릴리스 배포와 읽기 전용 점검, 아래쪽은 위험도에 따라 갈라지는 조치 경로이고, 카드 오른쪽 위 꼬리표는 그 단계가 실행되는 곳(컨트롤 노드 · 대상 서버)입니다.

![점검·조치 엔진 — 점검 스크립트 · 조치 스크립트 · 공통 함수](https://raw.githubusercontent.com/g3onho/system-security-automation-project/main/docs/images/shell-scripts.png)

모든 점검 스크립트는 같은 모양입니다. 아래는 U-01(root 원격 접속 제한)을 요약한 것입니다.

```bash
readonly ITEM_CODE="U-01"
readonly ACTION_TAG="승인요청"          # 자동조치 | 승인요청
readonly SEVERITY="상"                  # 상 | 중 | 하

do_check() {
    val="$(sshd -T | awk '/^permitrootlogin /{print $2}')"   # 실제 적용값 우선
    case "$val" in
        no|prohibit-password|without-password) return "$KISA_EXIT_GOOD" ;;  # 0 = 양호
        yes|"")                                 return "$KISA_EXIT_VULN" ;;  # 1 = 취약
    esac
}

verify_and_get_status do_check          # 같은 판정을 두 번 실행해 비교
print_json_result ...                   # 공통 형식의 JSON 출력
```

- 판정은 종료 코드로 합니다. 양호 `0`, 취약 `1`, 판정 불가 `2`.
- `verify_and_get_status`는 판정 함수를 **두 번** 실행합니다. 두 결과가 다르면 점검 도중 설정이 바뀐 것이므로 믿을 수 없다고 보고 `fail`로 처리합니다.
- 설정이 없거나 해석할 수 없으면 양호로 넘기지 않습니다. 보안 점검에서 "모르면 통과"는 가장 위험한 기본값이기 때문입니다.
- 판정 근거는 `detail`에 문장으로 남깁니다. 이 문장이 그대로 보고서의 "진단 근거"가 됩니다.

### 67번 접속하지 않기: 배치 실행기

항목마다 원격 접속하면 UNIX만 해도 SSH 왕복이 67번입니다. 그래서 대상 서버에 실행기(`run_checks.sh`)를 두고 **원격 호출 한 번으로 전 항목을 실행**합니다.

실행기는 항목마다 제한 시간(기본 120초)을 겁니다. 시간 초과, 스크립트 누락, 규약 밖 종료 코드, 잘못된 JSON은 모두 `fail` 결과로 바꿔서 결과 개수가 줄지 않게 했습니다.
그리고 `check.yml`이 결과를 받으면 **개수·중복·누락을 검증**합니다. 67개 중 하나라도 빠지면 그 점검은 실패입니다. 결과가 조용히 비는 걸 막기 위해서입니다.

### 공통 결과 형식 (스키마)

세 영역 모두 같은 형식의 JSON을 냅니다.

```json
{ "code": "U-02", "title": "비밀번호 관리정책 설정",
  "status": "취약", "severity": "상", "action_tag": "자동조치",
  "detail": "비밀번호 관리정책 미흡: 최근 비밀번호 기억=미적용(4회 이상 및 PAM 연동 필요)",
  "impact": "설정 파일 값만 변경되며 서비스 재시작이 불필요함",
  "os_type": "rocky 9.8", "release_hash": "0159deaf…", "duration_seconds": 0 }
```

결과 코드의 앞부분(`U-`, `WEB-`, `D-`, 코드 접두사)만 보면 영역을 알 수 있으니, **하나의 DB·채점 로직·화면으로 세 영역을 관리**합니다. 버전 표시(`release_hash`)로는 어떤 버전의 스크립트로 점검했는지까지 추적할 수 있습니다.

### 모든 조치를 자동으로 하지 않는다

조치는 서비스에 주는 영향으로 나눴습니다.

| | 자동조치 (39개) | 승인조치 (64개) |
|---|---|---|
| 예시 | 비밀번호 정책 값 변경 (U-02) | root 원격 접속 차단 (U-01), 계정 잠금 (U-03) |
| 서비스 영향 | 없음 | 접속·세션에 영향 가능 |
| 잘못되면 | 백업으로 바로 복구 | 관리자도 접속 못 할 수 있음 |
| 실행 조건 | 점검 직후 자동 (`audit.yml`) | 관리자가 고른 코드 + 확인 플래그 (`remediate_approved.yml`) |

절반이 넘는 64개를 승인요청으로 분류했습니다. 보수적으로 보일 수 있지만, 로그인 인증 설정(PAM) 하나를 잘못 건드리면 SSH·콘솔·su가 한꺼번에 잠긴다는 걸 생각하면 이게 맞다고 판단했습니다.

조치 스크립트에도 공통 규칙을 뒀습니다.

1. 승인요청 항목은 `KISA_APPROVAL=true`가 없으면 스스로 조치를 보류합니다. 플레이북을 잘못 실행해도 스크립트에서 한 번 더 막힙니다.
2. 바꾸기 전에 원본을 백업하고, 파일 이름에 백업 시각(타임스탬프)을 붙입니다.
3. 조치 후 같은 판정 함수를 두 번 실행해 최종 상태를 정합니다. "스크립트가 끝났다"가 아니라 "다시 봤더니 양호다"여야 조치 성공입니다.
4. 허용 IP처럼 관리자만 알 수 있는 값이 필요한 항목(TCP Wrappers, NFS, SNMP 등)은 값이 없으면 조치하지 않습니다.

### 무결성 있는 배포

점검 스크립트가 바뀌면 결과를 믿을 수 없습니다. 그래서 스크립트는 **검증 가능한 릴리스**로만 배포합니다.

- 컨트롤 노드에서 `check/ fix/ lib/` 파일마다 지문 같은 값(SHA-256 해시)을 계산해 목록(manifest)을 만들고, 그 목록의 해시를 버전 번호(릴리스 ID)로 씁니다. 내용이 같으면 번호도 같습니다.
- 대상 서버에 같은 릴리스가 이미 검증된 상태로 있으면 전송을 건너뜁니다.
- 새 버전은 임시 폴더에 풀고 목록 해시·파일 개수·스크립트 개수·바로가기 파일(심볼릭 링크) 여부를 검증한 뒤에만, "현재 버전" 바로가기(`current`)를 **한 번에 바꿔 끼웁니다**(원자적 교체).
- 배포 중에는 다른 작업이 못 들어오게 잠그고(배타 잠금), 점검끼리는 같이 돌 수 있게(공유 잠금) 해서 배포 중에 점검이 섞이지 않게 했습니다.

## 4. 실행 제어 · 신뢰 설계 — 실행하기 전에 검증한다

SSAP는 root 권한으로 설정을 바꾸는 도구입니다. 그래서 원격 작업 전에 확인하는 단계를 두었습니다.

**사전점검 게이트.** 모든 작업은 서버마다 다섯 가지를 확인합니다.

| 순서 | 검사 | 통과 조건 |
|---|---|---|
| 1 | SSH 신원 | 승인된 호스트 키 또는 CA 인증서와 일치 |
| 2 | SSH 인증 | 비밀번호 대신 키 파일로 로그인 성공(공개키 인증) |
| 3 | 지원 OS | Rocky / RHEL / CentOS / AlmaLinux / Ubuntu / Debian |
| 4 | 관리자 권한 | 비밀번호를 묻지 않고 관리자 권한 사용 가능(`sudo -n`, 비대화형 sudo) |
| 5 | 작업 충돌 | 같은 서버에 실행 중인 작업 없음 |

하나라도 실패하면 원격 작업은 시작하지 않고, 실패한 검사와 직접 확인할 명령어를 대시보드에 보여 줍니다. 앞 단계가 실패하면 뒤 단계는 "건너뜀"으로 표시해 원인을 한 곳으로 좁힙니다.

**작업 러너와 서버 단위 잠금.** 작업 요청이 오면 화면을 기다리게 하지 않고 뒤에서(백그라운드) `사전점검 → 배포 → 점검 → 적재 → 자동조치 → 적재` 순서로 실행합니다. 시작할 때 대상 서버에 잠금을 걸어 한 서버에서 두 작업이 겹치지 않게 했고, 플레이북 실행 제한(30분)과 오래된 잠금 정리(35분)를 둬서 작업이 멈춰도 서버가 영원히 잠기지 않게 했습니다. 작업이 실패해도 증적 생성과 잠금 해제는 반드시 실행됩니다.

**인증과 인벤토리.** 비밀번호는 원래 값으로 되돌릴 수 없게 변환한 값(PBKDF2 해시)으로만 저장하고, 로그인하면 받는 접속 키(세션 토큰)도 원문 대신 해시만 저장해 8시간 후 만료됩니다. SSH 지문 승인 · CA 초기화 · 인증서 배포처럼 신원을 바꾸는 API는 로그인 상태(세션 토큰)를 확인하고 관리자 비밀번호를 한 번 더 받습니다. 서버를 등록·삭제하면 Ansible 인벤토리를 다시 만드는데, 반쯤 쓰인 파일을 읽지 않도록 임시 파일에 다 쓴 뒤 한 번에 바꿔 끼웁니다(원자적 교체).

## 5. 결과 · 증적 · 보고 설계 — 다시 확인할 수 있게 남긴다

**데이터 모델.** MySQL에는 서버×항목별 최신 결과(`check_results`)와 실행할 때마다의 이력(`check_runs`)을 따로 둡니다. 결과 JSON은 컬럼으로 쪼개지 않고 원문으로 저장해, 점검 필드가 늘어나도 DB 구조(스키마)를 바꾸지 않게 했습니다. 작업 상태·잠금·SSH 신원 같은 운영 상태는 SQLite로 분리했습니다.

**작업 증적.** 작업이 끝나면 작업마다 증적 디렉터리를 만듭니다. 작업 정보(메타데이터), 실행 로그(비밀번호·토큰 값은 가림), 해당 작업의 결과 JSON을 모으고, 파일마다 위·변조를 확인할 해시값(SHA-256)을 계산해 `manifest.sha256`에 기록합니다. 대시보드에서 ZIP으로 내려받을 수 있습니다.

![작업 증적](https://raw.githubusercontent.com/g3onho/system-security-automation-project/main/docs/images/evidence-sha256.png)

**보고서와 점수.** Excel은 다운로드할 때마다 그 시점 DB로 새로 만들고, PDF는 원하는 IP·범위만 골라 항목별 진단 근거와 작업 해시까지 담아 출력합니다.
결과를 한눈에 보기 위한 보안 점수는 항목 중요도에 따라 상 10 · 중 8 · 하 6점을 배점하고, 취약이면 100%, 일부조치면 50%를 감점해 100점 만점으로 환산합니다. 양호율로는 "root 원격 접속 허용(상)"과 "불필요한 그룹 존재(하)"가 똑같이 1건이지만, 가중 점수에서는 중요한 항목이 취약할수록 크게 깎입니다. 실제로 같은 날 점검한 두 서버는 양호율이 비슷했지만, 상 등급 취약이 6건인 webs가 90.8점(양호), instructor_db가 92.2점(우수)으로 등급이 갈렸습니다.

### 6-1. SSH Host CA — 접속한 서버가 정말 그 서버인가

**문제를 발견하다.** 프로젝트 초반 Ansible 설정에는 이 줄이 있었습니다.

```ini
host_key_checking = False
```

처음 접속하는 서버마다 "이 서버의 호스트 키를 신뢰하시겠습니까?"를 묻지 않게 해 주는 설정입니다. 자동화에서 흔히 쓰고, 덕분에 플레이북이 막힘없이 돌았습니다.
그런데 앞에서 본 것처럼 SSAP는 대상 서버에 **root 권한으로 설정 파일을 바꾸는** 도구입니다. 호스트 키 검증을 끄면, IP가 바뀌었거나 다른 서버가 대신 응답해도 아무 의심 없이 그 서버를 "조치"합니다. 보안 점검 도구가 오히려 사고의 원인이 될 수 있었습니다.
그렇다고 검증을 그냥 켜면, 서버마다 호스트 키를 확인하고 등록하는 일이 서버 수만큼 생깁니다. 여러 대의 서버를 자동으로 점검하려는 프로젝트에서 이건 금방 감당하기 어려워집니다.

**선택지.**

| 방식 | 장점 | 단점 |
|---|---|---|
| 호스트 키 검증 끄기 (기존) | 편함 | 접속 대상을 전혀 확인하지 않음 |
| 서버별 호스트 키 수동 등록 | 안전 | 서버 수만큼 키 관리, 재설치마다 재등록 |
| SSH Host CA | CA 공개키 한 줄로 전체 신뢰, 만료·폐기를 한곳에서 관리할 수 있는 구조 | 첫 신뢰를 맺는 절차가 필요 |

SSH Host CA를 골랐습니다. CA가 각 서버의 호스트 키에 서명하고, 컨트롤 노드는 **CA 하나만 신뢰**합니다.
처음 등록하는 서버는 아직 인증서가 없으니, 첫 등록 서버는 **서버 콘솔에서 직접 확인한 호스트 키 지문(SHA256 해시)과 네트워크로 조회한 지문을 대조해 승인(trusted)한 뒤** 인증서를 배포합니다. 실습 편의를 위해 처음 본 키를 바로 신뢰하는 bootstrap 경로도 두었고, 이 경로는 감사 로그에 `auto_trusted_lab`으로 따로 남습니다.

**왜 SSH Host CA였나.** 실습에서 다룬 서버는 3대뿐이지만, 이 프로젝트가 지향하는 것은 **여러 대의 서버를 한 번에 점검·조치하는 자동화**입니다. 그런데 모든 작업은 SSH로 접속해서 이뤄지고, 서버마다 호스트 키를 확인하고 등록하는 과정은 서버 수만큼 늘어납니다. 서버를 추가하거나 재설치할 때마다 키를 다시 맞춰야 해서, 대수가 많아질수록 SSH 연결을 관리하는 일 자체가 복잡해집니다.

SSH Host CA를 쓰면 컨트롤 노드는 **CA 공개키 한 줄만 신뢰**하면 되고, 서버는 CA가 서명한 인증서만 받으면 됩니다. 서버가 몇 대든 같은 신뢰 기준이 그대로 적용됩니다.

**완벽하지 않은 걸 알면서 왜 지금 넣었나.** 2주 실습에서 운영 수준의 CA(첫 신뢰 검증, CA 키 보호, 인증서 폐기·갱신)까지 만들 수 없다는 건 알았습니다. 그래도 서버가 3대일 때 이 구조가 실제로 동작하는지 먼저 확인해 두면, 서버가 늘어날 때 같은 방식으로 넓힐 수 있다고 판단했습니다. 대신 실습이라 생략한 부분은 숨기지 않았습니다. 처음 본 키를 바로 믿는 bootstrap 경로는 감사 로그에 `auto_trusted_lab`으로 따로 남겨, 실습용 경로라는 사실이 기록에 드러나게 했습니다.

전체 흐름을 먼저 그림으로 보면 이렇습니다. 서버 상태는 등록 직후(`pending`) → 지문 승인 완료(`trusted`) → CA 인증 완료(`certified`)로 올라가고, 승인한 키가 바뀌면 `changed`가 되어 작업이 막힙니다.

![SSH Host CA 신뢰 수립과 검증 흐름](https://raw.githubusercontent.com/g3onho/system-security-automation-project/main/docs/images/ssh-ca-flow-mine.png)

**구현.** CA 개인키는 `0600` 권한으로 두고, 저장 폴더(`runtime/`)는 Git에서 제외했습니다.

```bash
ssh-keygen -t ed25519 -N "" -C "SSAP lab SSH Host CA" -f runtime/ssh_host_ca

# 호스트 인증서 발급
ssh-keygen -s runtime/ssh_host_ca -h \
  -I "ssap:<hostname>:<ip>:<serial>" \
  -n "<hostname>,<ip>" \
  -V -5m:+52w \
  host_key.pub
```

- `-h` : 사용자가 아니라 **호스트** 인증서
- `-n` : 인증서에 들어갈 이름(principal). 호스트명과 IP를 둘 다 넣어 어느 쪽으로 접속해도 검증되게 했습니다.
- `-V -5m:+52w` : 시계 오차를 고려해 5분 전부터 52주 동안 유효. 만료가 있어야 방치된 신뢰가 남지 않습니다.

인증서를 쓰려면 대상 서버의 `sshd_config`를 고쳐야 합니다. 여기서 실수하면 SSH 데몬이 안 뜨고, 원격 서버에 다시 들어갈 길이 없어집니다. 그래서 순서를 엄격하게 지켰습니다.

```bash
backup=/etc/ssh/sshd_config.ssap-backup-$(date +%Y%m%d%H%M%S)
sudo cp -a /etc/ssh/sshd_config "$backup"
# ... 인증서 설치, HostCertificate 설정 추가 ...
if ! sudo sshd -t; then                 # 문법 검사 실패 → 원복
  sudo cp -a "$backup" /etc/ssh/sshd_config; exit 20
fi
if ! sudo systemctl reload sshd; then   # reload 실패 → 원복 후 재기동
  sudo cp -a "$backup" /etc/ssh/sshd_config; exit 21
fi
```

배포가 끝나면 네트워크로 인증서를 다시 조회해 CA 서명까지 확인하고, 확인하지 못하면 배포 실패로 처리합니다.
마지막으로 컨트롤 노드에 "이 CA가 서명한 서버만 믿는다"는 한 줄(`known_hosts`의 `@cert-authority`)을 넣고, 대시보드가 실행하는 모든 플레이북은 확인되지 않은 서버면 접속을 거부하게 했습니다(`StrictHostKeyChecking=yes`). 이 신원 확인이 사전점검 게이트의 1단계입니다.

![등록된 서버가 모두 CA 인증 상태](https://raw.githubusercontent.com/g3onho/system-security-automation-project/main/docs/images/ca-status.png)

![SSH Host CA 인증 상세 — 배포 검증 · 재검증 · 감사 이력](https://raw.githubusercontent.com/g3onho/system-security-automation-project/main/docs/images/ca-detail.png)

실제 대시보드의 CA 인증 상세 화면입니다. ① Host CA 준비 → ② 지문 승인 → ③ 인증서 발급·배포 → ④ sshd 반영 검증 → ⑤ 네트워크 재검증 순서가 그대로 보이고, 감사 이력에는 실습용 bootstrap(`auto_trusted_lab`)과 인증서 배포(`certificate_approved`)가 남아 있습니다.

**어디까지 했고, 무엇을 못 했나.**

*된 것*

- 등록 서버 3대에 인증서를 배포해 모두 certified(화면의 "CA 인증") 상태로 점검을 준비했습니다.
- 배포는 백업 → `sshd -t` → reload 순서로 하고, 실패하면 원복하는 경로까지 구현했습니다. 배포 후 다시 조회해 CA 서명을 확인한 서버만 certified가 됩니다.
- 대시보드가 실행하는 작업은 CA가 서명한 서버에만 접속하고(`@cert-authority`, `StrictHostKeyChecking=yes`), 아직 승인 전이거나(`pending`) 키가 바뀐(`changed`) 서버는 사전점검 1단계에서 차단됩니다.
- 첫 신뢰는 콘솔 지문 대조 승인으로 구현했습니다. 지문이 다르거나 조회 중 키가 바뀌면 거부합니다.
- 지문 승인·CA 초기화·인증서 배포는 관리자 비밀번호를 다시 확인하고, 성공·실패 모두 감사 기록에 남습니다.

*부분적으로 된 것*

- **첫 신뢰** — 처음 접속한 서버가 진짜인지 지문 대조로 확인하도록 만들었지만, 실습 편의를 위해 이 확인을 건너뛰고 처음 받은 키를 그대로 믿는 경로(bootstrap)도 남겨 두었습니다. 이 경로를 쓰면 기록에 `auto_trusted_lab`으로 표시되지만, 첫 접속 순간 가짜 서버가 응답하면 걸러내지 못합니다(TOFU의 한계).
- **검증 강제** — 대시보드 경로에만 적용됩니다. `ansible/unix`·`ansible/web`의 `ansible.cfg`는 `host_key_checking = False`라, 대시보드 없이 수동 실행하면 검증이 빠집니다.
- **CA 개인키 보호** — 권한 `0600`, Git 제외, 관리자 재확인까지만 했습니다. 키에 암호가 없고(`-N ""`) 대시보드와 같은 컨트롤 노드에 파일로 있습니다.

*하지 못한 것*

- 문제가 생긴 인증서를 바로 무효로 만드는 목록(KRL)과 만료 전 자동 갱신 — 키가 유출돼도 즉시 무효화하지 못합니다.
- CA 키를 안전하게 따로 보관하고 서명해 주는 장비·서비스(HSM·Vault)로 옮기는 것, CA 키 주기적 교체(rotation).
- 서버가 많은 환경에서의 검증.

정리하면 **"자동화가 엉뚱한 서버에 접속해 조치하지 않게 막는 장치"는 동작하지만, CA 자체를 지키는 운영 수준의 장치는 없다**가 이 구현의 정확한 범위입니다.

**운영으로 옮긴다면 이 순서로** — ① 수동 실행용 `ansible.cfg`도 호스트 키 검증 켜기(설정 한 줄) → ② bootstrap 경로를 막고 지문 대조 승인만 허용 → ③ CA 개인키를 별도 서명 서비스로 분리 → ④ KRL과 자동 갱신 추가.

### 6-2. 대시보드 개발 — 운영자가 판단할 것을 먼저 보여 주기

화면을 설계하면서 가장 신경 쓴 것은 **운영자가 "무엇을 직접 판단해야 하는지" 바로 보이게 하는 것**이었습니다.

먼저 구조입니다. 아래 그림은 기능(행)마다 화면 → API → 백엔드 모듈 → 저장소 → 외부 실행 순서로 읽으면 됩니다. 화면 3페이지(IP 등록 · 점검·조치 · 상세 분석)가 FastAPI REST API 27개를 호출하고, 점검·조치 요청은 작업 러너가 백그라운드로 실행합니다. 러너는 사전점검과 서버 잠금을 거친 뒤 `ansible-playbook`을 실행하고, 결과 JSON을 MySQL에 적재하며, 성공·실패와 관계없이 작업마다 증적 ZIP을 남깁니다.

저장소를 둘로 나눈 데도 이유가 있습니다. MySQL에는 화면과 보고서가 함께 읽는 결과 데이터를, SQLite에는 컨트롤 노드 한 곳에서만 쓰는 실행 상태(작업 · 잠금 · 신원 · 세션)를 두었습니다. 결과 DB에 문제가 생겨도 잠금과 신원 확인은 따로 동작합니다.

8월 30일 운영 상태 점검에서 자동조치 대상은 두 서버의 U-02(비밀번호 관리정책) 2건이었습니다.
자동조치를 실행했는데, 재점검 결과는 둘 다 **여전히 취약**이었습니다. 대시보드의 조치 업데이트에도 "미조치 2건"으로 그대로 표시됐습니다.

![조치 업데이트](https://raw.githubusercontent.com/g3onho/system-security-automation-project/main/docs/images/remediation-update.png)

원인은 이랬습니다.

- 조치 스크립트는 `login.defs`, `pwquality.conf` 값을 바꾸고, `pwhistory.conf`에 `remember = 4`까지 씁니다.
- 하지만 **로그인 인증 설정(PAM)에 비밀번호 이력 모듈(`pam_pwhistory`)을 연결하지는 않습니다.**
- 판정 기준은 "최근 비밀번호 4회 기억 + PAM 연동"이라, 설정 파일만으로는 양호가 될 수 없었습니다.

로그인 인증 설정(PAM)을 고치지 않은 건 의도된 것이었습니다. U-03(계정 잠금)을 승인요청으로 둔 것과 같은 이유, 즉 잘못 고치면 모든 로그인 경로가 잠길 수 있기 때문입니다. 그래서 자동조치 범위를 넓히는 대신, **남은 부분은 승인 경로로 처리할 항목**으로 판단했습니다.

이 일이 중요했던 이유는, 조치 스크립트의 종료 코드만 믿었다면 "조치 완료"로 기록됐을 것이기 때문입니다.
3장의 "조치 후 같은 판정을 다시 실행한다"는 설계와, 그 결과를 조치 전 상태와 나란히 보여 주는 화면이 **거짓 성공**을 막았습니다.

또 하나는 통합 테스트 때 대시보드 집계가 맞지 않았던 일입니다. 초기 DBMS 결과는 `rule`, 영문 `status`(`PASS`) 같은 다른 형식이었고, 조치 권한 필드도 없었습니다. 컨트롤 노드에 구버전과 신버전 결과가 섞여 있었던 거죠. 모든 영역을 공통 형식(스키마)으로 통일하고 나서야 하나의 DB와 화면으로 묶을 수 있었습니다.

## 8. 결과

2026년 8월 30일, 점검 대상 서버 2대 기준입니다.

- 서버 2대, **170개 항목**을 한 번에 점검
- 모든 작업이 사전점검 **10/10**(서버 2대 × 검사 5개)을 통과한 뒤 실행
- 취약 설정을 심어 둔 회차에서 **41건** 탐지 (상 23 · 중 13 · 하 5) — root와 같은 권한을 가진 다른 계정(UID 0), 비밀번호 없이 접속을 허용하는 파일(`.rhosts`), 로그인 없이 쓰는 FTP(익명 FTP), 누구나 접근 가능한 공유 폴더(NFS), 기본값 그대로인 장비 관리 비밀번호(SNMP community) 등
- 실행한 작업 **20건 모두** 로그·결과 파일 SHA-256 검증 통과

PDF 보고서에는 "승인조치 후 점수 100점"이라는 칸도 있습니다. 하지만 이 값은 남은 취약 항목을 **모두 조치에 성공했다고 가정한 예상치**입니다. 앞에서 본 것처럼 자동조치 2건조차 재점검에서 해결되지 않았기 때문에, 측정된 적 없는 이 숫자는 결과에서 뺐습니다.

## 9. 남은 숙제

- **판정 불가(N/A) 항목을 지표마다 다르게 셌습니다.** 자동 판정이 안 되는 D-06을 보안 점수는 100% 감점, Excel 준수율은 분모에서 제외, PDF는 취약으로 표기해서, 같은 회차인데 취약 건수가 화면에 따라 13건, 14건으로 달랐습니다. 상태 정의를 하나로 맞춰야 합니다.
- Windows 점검은 지원하지 못했고, DBMS는 MySQL 10개 항목에 그쳤습니다.
- 서버 장애나 네트워크 단절 같은 예외 처리를 더 보완해야 합니다.
- 로그인 상태 확인(세션 토큰 검사)을 SSH 신원 · CA API에만 적용했습니다. 점검 실행 · 결과 조회 API까지 같은 인증을 거치도록 넓혀야 합니다.
- 지금의 Host CA는 실습용입니다. bootstrap 경로를 막고 지문 승인만 허용하고, CA 개인키를 안전한 보관 장비·서비스(Vault·HSM)로 옮기고, 인증서 폐기 목록(KRL)·자동 갱신을 넣고, 수동 실행용 `ansible.cfg`도 호스트 키 검증을 켜야 합니다(6-1의 표).

## 10. 돌아보며

- **자동화 도구도 공격받을 수 있는 지점(공격 표면)이다.** "편하니까 끄자"던 설정 하나가, root로 설정을 바꾸는 도구와 만나면 큰 위험이 됩니다.
- **바꾸는 작업은 되돌릴 수 있어야 한다.** 백업 → 검사 → 적용 → 실패 시 원복.
- **조치와 해결은 다르다.** 재점검으로 확인하기 전까지는 고쳐진 게 아닙니다.
- **형식을 먼저 합의해야 한다.** 결과 형식(스키마)을 늦게 통일한 대가를 통합 테스트에서 치렀습니다.

2주라는 짧은 기간이었지만, "점검을 자동화한다"는 목표 안에 "자동화 자체를 안전하고 정직하게 만든다"는 숙제가 숨어 있다는 걸 배운 프로젝트였습니다.
